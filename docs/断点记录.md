# 断点记录

## BP-001（2026-09-13）

### 状态

这是 Phase 1 初期的历史阻断记录；better-sqlite3 路线已放弃，node:sqlite 实现已完成本地验证，Node 22.13+ CI 仍按 BP-010 单独待验证。

### 事实

1. `better-sqlite3@12.4.1` 的安装脚本是在获得明确批准后执行的。
2. 预编译包因网络断开未取得。
3. 安装过程转入 `node-gyp` 本机构建后，因本机没有 Visual Studio C++ 工具链而失败。
4. 该安装阻断了 `EPIC-002` 的 SQLite adapter 工作。
5. 只读探测确认 Node.js `v24.19.0` 与 `v24.15.0` 均可使用内置 `node:sqlite` 的 `DatabaseSync`，并在内存数据库中执行建表、插入和查询。
6. 当前 `docs/ADR/ADR-0001-sqlite-wal.md` 仍记录 `better-sqlite3` 为初始驱动；本次只建立本记录，未修改该 ADR、依赖配置或实现代码。

### 推断

1. 当前阻断主要来自 `better-sqlite3` 预编译包获取及本机构建链，而不是 SQLite 基础建表、写入和查询能力已被证明不可用。
2. `node:sqlite` 的 `DatabaseSync` 已显示出作为替代运行时入口的可行性，但现有内存数据库探测不足以证明其满足文件库、并发、崩溃恢复和项目 API 契约。

### 解决方案

当前采用 Node.js 内置 `node:sqlite` 的 `DatabaseSync` 作为 SQLite adapter 的实现方向，以解除对 `better-sqlite3` 原生安装链的依赖。

本断点只记录方案方向，不在本次操作中实施代码、依赖、CI 或 ADR 改造。

### 历史待验证项

以下项目均尚未验证：

1. Node 22.13+ CI 兼容性与测试结果（22.5 起提供模块，但 22.13 起无需实验 flag）。
2. 文件数据库上的 WAL 行为。
3. 并发访问与崩溃恢复行为。
4. `node:sqlite` 对项目所需 API 的类型支持与 TypeScript 类型检查结果。

### 用户决策（建档时）

1. 当前 SQLite adapter 方案采用 `node:sqlite`。
2. 建档时本次工作范围仅限建立并填写 `docs/断点记录.md`；不修改其他文件、不提交、不联网。

### 后续落实（2026-09-13）

用户随后授权继续 Phase 1，并明确采用内置 `node:sqlite`。主代理据此移除了未进入基线的 `better-sqlite3` 依赖，更新了 SQLite ADR、Node.js 最低版本和 CI 约束，并开始实现事件账本。

这些改动不改变本断点中的失败事实；它们把“待验证的替代方案”推进为“正在验证的实现方案”。文件数据库 WAL、迁移事务、并发写入、崩溃恢复、Node 22.13+ CI 和 TypeScript/API 兼容性仍须以 Phase 1 测试证据为准。

## BP-004（2026-09-13）

### 状态

多进程首次打开同一个新文件库时发现迁移启动竞争；已定位原因、修正实现并通过全量 verify。

### 事实

1. 四个独立 Node 进程同时构造 `SqliteEventStore` 时，其中一个进程成功创建并记录 `0001_init`。
2. 另一个进程在自身读取 `schema_migrations` 后才等待写锁，因此仍依据过期的空结果尝试插入同一迁移版本。
3. 该进程收到 `UNIQUE constraint failed: schema_migrations.version`，导致并发测试在业务事件断言前退出。
4. 同轮独立的崩溃恢复测试通过，说明该失败点位于迁移启动竞争，而不是未提交事件的回滚路径。

### 推断

迁移器原先把“读取已应用迁移”和“获得写锁并应用迁移”拆成了两个竞争窗口；`busy_timeout` 只能等待锁，不能替过期快照重新计算迁移状态。若不修正，多个 daemon/worker 首次启动会把正常的初始化竞争误报为迁移损坏。

### 解决方案

将 `BEGIN IMMEDIATE` 提前到读取 `schema_migrations` 之前，把迁移状态校验、迁移 SQL 和版本记录合并进同一个事务。`applyMigration` 不再嵌套开启/提交事务，由外层事务统一负责原子性；等待锁的进程在前一个进程提交后重新读取已应用版本。

### 验证结果

构建产物上的新库并发初始化、共享 eventId/operationId 幂等竞争、不同 eventId/相同 operationId 冲突、事件 `seq` 连续性和 WAL 资源回收均通过：4 个独立进程各写入 24 个唯一事件，另有 2 个共享竞争事件，共 98 行。Node 22.13+ CI 仍需由远程 runner 提供该版本实测证据。

## BP-006（2026-09-13）

### 状态

仓库级 verify 曾在 dependency-cruiser 的合法 workspace import 解析处失败；已修正分析配置并通过全量 verify。

### 事实

1. Phase 1 首次加入 `packages/store/src/sqlite.ts` 到 `@praxis/contracts` 的 workspace import 后，TypeScript、构建和 Node ESM 运行均正常。
2. dependency-cruiser 从根目录按 CommonJS/Node 模块解析时，无法把仅声明 `types`/`import` 条件的 ESM workspace export 解析成依赖，报告 `no-unresolved`。
3. 该报告不是运行时找不到模块；`import.meta.resolve` 在 `packages/store` 目录可解析到 `packages/contracts/dist/index.js`。

### 推断

运行时模块解析和静态架构图解析使用了不同的条件与入口。若直接放宽 `no-unresolved`，会牺牲对真正跨包断裂的检测；应为图分析提供独立的 source-entry alias，而不改变 Node 运行时包出口。

### 解决方案

新增 `tsconfig.dependency-cruiser.json`，把 `@praxis/*` 映射到 `packages/*/src/index.ts`（并为 apps 保留兜底），仅由 dependency-cruiser 使用；`.dependency-cruiser.cjs` 指向该分析配置，运行时 package exports 不变。修正后边界检查报告 23 个模块、23 条依赖、0 violations。

### 验证结果

当前 source graph 与运行时解析均已验证。后续新增 workspace package 或改变 package exports 时，仍必须同时验证 TypeScript/Node 运行解析和 dependency-cruiser source graph 解析，不能只依赖其中一套结果。

## BP-009（2026-09-13）

### 状态

Phase 1 双代理审查发现原始 SQLite 句柄越过 Event Store 边界；该 Critical 问题已修正，新的契约与完整性测试已通过本地复测，Node 22.13.0 CI 仍是独立待办。

### 事实

1. 初版 `SqliteEventStore` 为了让集成测试读取迁移表和让并发脚本执行 checkpoint，公开了 `database` 属性。
2. 该属性能够执行任意 SQL，理论上可绕过 append-first、事件校验、content hash 和 provenance，直接修改或删除原始事件。
3. 这不是“测试代码才会这样用”的充分理由；公共 API 一旦允许该路径，未来 Agent/Tool 消费者就可能形成未经审计的旁路。

### 推断

原始事实的不可静默覆盖要求必须在对象边界上成立，不能只写在 README 或调用约定里。测试所需的故障注入能力与生产消费者所需的 EventReader/EventWriter 能力必须分开。

### 解决方案

1. 将 SQLite 连接改为 ECMAScript `#database` 私有字段，不再从 `SqliteEventStore` 公共 API 暴露。
2. 以只读的 `migrationVersion` 和既有 `pragmas` 提供有限诊断信息；集成测试不再查询任意 SQL。
3. 将 `MigrationRunner` 从 `@praxis/store` 公共 index 移除；崩溃夹具通过明确标注的构建产物内部入口执行故障注入。
4. `close()` 内部负责 WAL checkpoint；增加 provenance/evidence/links round-trip 和 payload 篡改后 content hash 拒绝测试。

### 验证结果

类型、lint、测试（13 tests）、构建、并发、崩溃恢复和全量 verify 均通过；事件对象不再暴露 `database` 属性，篡改 payload 后读取会因 content hash mismatch 被拒绝。另需保持 Node 22.13.0 CI 证据为独立待办，不以本机 Node 24 结果替代。

## BP-011（2026-09-13）

### 状态

工程审查发现两处会静默破坏原始事件材料或 append 原子性的实现缺陷，均已修正并加入回归测试。

### 事实

1. `Date.parse` 会接受 `2026-02-30T00:00:00.000Z` 并规范化为另一天；若读回校验在 commit 后失败，会出现“调用报错但行已写入”。
2. `stableStringify` 原先用普通对象承载规范化结果，赋值合法 JSON 键 `__proto__` 时会触发原型特殊行为并丢字段。

### 解决方案

1. 时间契约增加 canonical 字符串回转校验：`Date.parse(value)` 后的 `toISOString()` 必须与原字符串完全相同；插入后的读回契约与哈希校验移到 `COMMIT` 之前。
2. 规范化对象改用无原型对象，并使用确定的 UTF-16 代码单元比较排序；增加非法日期、`__proto__` 保留、篡改 payload 拒绝和 provenance/evidence/links 往返测试。

### 验证结果

本地 Node 24.15.0 下单元/集成测试已从 12 个增加到 13 个，并发和崩溃恢复夹具继续通过；Node 22.13.0 runner 仍按 BP-010 待验证。

## BP-012（2026-09-13）

### 状态

迁移完整性与测试夹具边界已按工程审查要求补强，并已通过本地完整性与复杂夹具复测；Node 22.13+ runner 仍是独立待办。

### 事实

1. 原迁移元数据只保存 version/name，已应用 SQL 被同名修改时不会被识别。
2. 并发夹具原先只用同 eventId + operationId 的共享事件，不能单独证明不同 eventId 复用 operationId 会被拒绝。
3. 子进程原先监听 `exit` 且没有超时；crash worker 的输出也可能在立即退出时被截断。
4. `pnpm-workspace.yaml` 仍残留已移除的 `better-sqlite3` build allowlist；崩溃夹具依赖的内部迁移构建入口没有在 package build 命令中明确声明。

### 解决方案

迁移表增加 SQL SHA-256 checksum，要求版本从 1 连续递增，并在同一写事务内校验历史迁移；并发夹具增加不同 eventId/相同 operationId 的竞争断言；子进程改用 `close`、15 秒超时和稳定的输出收尾；store build 显式包含内部 migrations entry，移除过时的 native dependency allowlist。

### 验证结果

全量 verify 已确认 migration checksum、operationId 竞争、子进程收尾、构建入口和清理路径同时通过；并发脚本报告 98 行，崩溃恢复脚本通过。

## BP-013（2026-09-13）

### 状态

最新全量 verify 暴露连接初始化阶段的 WAL 切换竞态：多个进程同时执行 `PRAGMA journal_mode = WAL` 时，busy timeout 尚未设置，出现 `database is locked`。已把 busy timeout 提前到第一条连接 PRAGMA，并通过重复并发复测。

### 事实

1. 迁移事务已经有 `BEGIN IMMEDIATE` 与 busy timeout，但它们尚未执行到连接配置失败的进程。
2. `journal_mode` 切换本身可能需要等待其他进程完成文件库初始化；原顺序在等待机制建立前就执行了该语句。
3. 该失败发生在数据库打开/配置阶段，不是事件计数、幂等或崩溃恢复断言失败。

### 解决方案

`SqliteEventStore.configureConnection()` 与 crash worker 统一先执行 `PRAGMA busy_timeout = 5000`，再切换 WAL、打开外键和设置同步级别；后续需用重复独立进程矩阵证明初始化锁竞争可恢复。

### 验证结果

构建产物上的并发夹具重复 6 轮（每轮 4 个独立进程、98 行）和崩溃恢复重复 4 轮均通过；system Node 24.15.0 与 bundled Node 24.19.0 各自的并发/崩溃检查也通过。Node 22.13.0 runner 仍按 BP-010 待验证。

## BP-014（2026-09-13）

### 状态

并行执行 `typecheck` 与 `test` 时发现 Vitest 通过 workspace package export 读到旧的 `contracts/dist`，导致源码已拒绝的非法日期在集成测试中先插入、再以 content hash mismatch 报错；已增加 Vitest source alias，并确认独立 `pnpm test` 通过。

### 事实

1. 仓库的生产 package export 指向 `dist`，而集成测试直接导入 store 源码；store 源码中的 `@praxis/contracts` 若未先重建，会解析到旧 dist。
2. 并发运行 typecheck/build 与 test 会放大该时间窗口，造成“代码和测试看似来自同一工作树、实际使用两套契约”的错配。
3. 这不是账本语义的新失败，但会使回归测试不稳定并掩盖真正的 `INVALID_EVENT` 边界。

### 解决方案

## BP-044（2026-09-15）

### 工具链在源文件中引入控制字符

Phase 5 实现期间发现两处**写入通道引入的静默损坏**：`scanner.ts` 中用于拼接异常合并键的分隔符被写成了真实 NUL 字节（`�` 转义被管道解释为控制字节而非四字符文本），`archive.ts` 中一个本意为"控制字符区间"的正则字符类被写成了字面 NUL 与 US 两个字符。

### 事实

1. 两处都不是设计错误，而是**编辑器/工具链把转义序列实体化**的结果；`git` 与 `grep` 随后把 `scanner.ts` 判为二进制文件，是这次损坏第一次显形的地方。
2. `archive.ts` 的字面控制字符使该正则实际只匹配 NUL 与 US，**漏掉 0x01–0x1E 的其余控制字符**——一个真实的安全校验缺口，而非仅格式问题。
3. `scanner.ts` 的 NUL 分隔符功能上可用，但使合并键不可读、不可 grep，且依赖一个不可见字符做边界。

### 解决方案

1. `scanner.ts` 改为**对每个分量分别取摘要后再拼接**（`.map(part => sha256Hex(part).slice(0,16)).join("-")`），彻底不依赖任何分隔符字符：没有分量能伪造边界，也没有不可见字符进入源码。
2. `archive.ts` 改为**按码点判断**（`codePoint < 32 || codePoint === 127`）加一个显式禁止字符集合 `["<", ">", "\"", "|", "?", "*"]`，不再使用正则字符类区间。
3. 新增守护：Phase 5 的所有新源文件在提交前逐字节扫描控制字符，确认 `scanner.ts`、`archive.ts` 归零。

### 边界与后果

这是一次**工具链层的断点**，不是运行时缺陷：`pnpm verify` 在损坏存在时仍然通过，因为 NUL 分隔符在功能上等价。它的价值在于暴露了一个更一般的风险——**只有当文本被当作字节检查时才会显形的损坏**。这与第一代语料的 BOM/CRLF 问题、以及本仓库 BP-040 的 Windows 换行问题属于同一族：**表示层的差异不进入断言，就不会被发现**。

## BP-045（2026-09-15）

### Phase 5 实现期三个真实缺陷

### 事实

1. **路径限定错配**：`scanner.ts` 的 `findFile` 用未限定的相对路径（`.signals_index.json`）去匹配已限定的 `entry.relativePath`（`<root>/.signals_index.json`），导致索引文件**永远找不到**，signal 采集静默返回空数组。单元测试首次运行即捕获。
2. **异常标识碰撞**：异常 id 最初只取合并键的一部分（类别 + 声明值）取摘要，同一类别下不同 reason/路径的异常会得到**相同 id**，触发 `legacy_anomalies` 主键冲突，整个导入事务回滚。
3. **append-only 与回填冲突**：`legacy_import_runs` 被设计为 append-only（含 no-update 触发器），但首版实现先插入 run 行、追加事件后再 `UPDATE ... SET last_seq`，被自己的触发器拒绝。

### 解决方案

1. `ScannedFile` 增加 `key` 字段保存**未限定的相对路径**，`findFile` 按其匹配；限定路径仍用于清单审计与事件 payload。
2. 异常 id 改为 `类别 + sha256(整套合并键)`，使合并语义与标识语义一致：同键合并、异键区分。
3. 调整写入顺序为**先追加事件、再一次性插入 run 行**（`last_seq` 随插入写入），既保持表真正 append-only，又保持单事务原子性。

### 验证结果

全部 125 个测试与 Phase 1–5 场景通过。这三个缺陷都不是"测试写错"，而是实现错误；前两个若未被测试覆盖，会分别表现为**静默的数据丢失**与**导入整体失败**。

## BP-047（2026-09-16）

### 状态

**已修复（2026-09-16，业主决策：纠正 doctor 分类）。** 这是 Phase 5 期间由回归测试顺带发现的**既有缺陷**（托管备份机制来自 Phase 3.5/ADR-0010），不属于 Phase 5 新增范围，因此发现时只记录、未擅自修改。业主在 Phase 5 收尾汇报后选择候选修法 C，实施见"用户决策与实施"。Phase 5 的恢复行为改动（见"边界"）保留。

### 事实

1. `createManagedBackup`（`packages/store/src/sqlite.ts`）的执行顺序是：`reserveManagedBackup` 先向**活动数据库**的 `managed_backups` 表插入一行占位记录（`backup_sha256 = ''`，`status = 'active'`），再调用 `backupTo` 执行 `VACUUM INTO` 生成备份文件，最后由 `registerManagedBackup` 把该行更新为最终摘要。
2. `VACUUM INTO` 是**整库在线快照**，因此它把"尚未定稿的占位行"一并复制进了备份文件本身。备份完成后活动库的那一行被 `UPDATE` 定稿，但**备份文件里的那一行永远停留在空摘要状态**。
3. 备份文件旁**不写任何清单文件**：`backupTo` 只返回 manifest 对象，摘要只存在于活动库的行里。因此备份文件内部的那条空摘要行**无法自证**——它所在的数据库里没有任何东西能证明它的摘要应该是多少。
4. `getHealth` 把 `status = 'active'` 的行一律按已定稿备份检查：`existsSync(path)` 通过后比较 `sha256File(path) !== backup_sha256`，空摘要必然不等于真实摘要，于是该行进入 `invalidChecksums`。
5. 运行时 doctor 检查 `managed-backup-integrity` 只要 `invalidChecksums` 非空即判 `fail`（`packages/runtime/src/index.ts`）。
6. 后果：**从任一托管备份恢复出来的数据库，都无法通过它自己的 doctor 门禁。** 即 ADR-0010 设计的主要灾难恢复路径，恢复成功之后立刻被自己的完整性检查判为不健康。

### 复现

`tests/integration/phase5-review-fixes.test.ts` → `describe("backup restore")`。两次 `backup create` 后两次 `backup restore`，两次都以退出码 5 结束，错误详情 `failingChecks` 含 `managed-backup-integrity`。人工检查恢复副本的 `managed_backups` 行：`{"status":"active","backupSha":""}`。

### 为什么不能顺手改

1. 这属于 ADR-0010 冻结的备份语义，改动会使已冻结的契约与既有备份文件的可信性发生变化。
2. 三种候选修法各有实质代价，且取舍取决于业主对"崩溃可见性"与"恢复可用性"的偏好，不是实现细节（见下）。
3. 本项目的原则是**发现的问题记录为问题，不静默修复**（同 BP-044 的处理方式）。

### 候选修法（待决策）

| 方案          | 做法                                                                                                                       | 代价                                                                                                                                     |
| :------------ | :------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| **C（推荐）** | 只改 doctor 的分类：`backup_sha256 = ''` 的 active 行不再算"校验和不匹配"，另立 `unfinalizedReservations` 计数字段单独披露 | 最小改动、不动任何写入语义；但它承认"未定稿的预留"在健康检查中不等于失败，削弱了对真实崩溃残留的告警强度                                 |
| **D**         | 恢复时用 `restore` 已经验证过的 manifest 回填恢复副本里那一行的摘要                                                        | 让恢复副本自洽；但这是**对已恢复内容做写入**，触及 ADR-0010 语义，需要业主明确授权                                                       |
| **E**         | 把 `reserveManagedBackup` 的插入移到 `VACUUM INTO` 之后                                                                    | 快照里只留已定稿行；但**丢失崩溃可见性**——进程在备份中途崩溃时，残留的 `*.backup-pending-*` 暂存文件将不再被 doctor 看见（目前能被看见） |

推荐 C：它是对**诊断标签**的纠正而不是对语义的改动——那一行本来就是"未定稿的预留"，把它叫作"校验和不匹配"是检查说错了话，不是数据错了。若业主希望恢复副本自洽，C+D 组合使用。

### 边界

1. 该缺陷**不是 Phase 5 引入的**：Phase 5 之前 `backup restore` 同样会失败，只是失败后把恢复结果留在原地、由操作员自行处置。
2. Phase 5 在 CLI 侧加了**恢复后回滚**（补丁 `patch5b.py`）：恢复副本 doctor 失败时，先取回维护锁、把安全副本写回目标路径、重新打开并重建投影，再把失败抛出，错误详情携带 `failingChecks`。因此该既有缺陷现在的表现是**恢复被干净地拒绝并回滚**，而不是留下一个半恢复的库。这个改动本身是正确的（失败即关闭），但它把一个潜伏缺陷变成了灾难恢复路径上的**硬阻断**，提高了本条的处置优先级。
3. 同一轮的 Phase 5 修复已经消除了另一个更早的阻断（固定名安全副本导致第二次恢复直接拒绝），由同一测试覆盖。

### 用户决策与实施（2026-09-16）

**决策：候选修法 C——纠正 doctor 的分类。**

实施内容：

1. `getHealth` 把 `status = 'active'` 的行先按**是否已记录摘要**分开：摘要为空的行进入新的 `managedBackups.unfinalizedReservations`，**不再参与** `sha256File(path) !== backup_sha256` 比较。已记录摘要的行仍按原样比较。
2. `managed-backup-integrity` 检查的**失败条件不变**（仍是 `missingFiles` 或 `invalidChecksums` 非空），只在 `message` 中披露未定稿预留的数量，并把整个 `managedBackups` 放进 `details`。因此"未定稿"是**披露**而不是**放行**。
3. 关键区分被写进代码注释：**摘要缺失与摘要不符是两种状态**，只有第二种才是"备份文件被改过"的证据。

验证（`tests/integration/phase5-review-fixes.test.ts`，同一文件三个用例）：

- 连续两次 `backup restore` 现在都**成功**（退出码 0），而修复前两次都退出 5。灾难恢复路径可用。
- 恢复副本的 doctor **仍披露** `unfinalizedReservations: 1`——状态可见，只是不再被叫作损坏。
- 新增回归用例：把一个托管备份文件的字节改掉后，`doctor` **仍然**退出 6 并给 `managed-backup-integrity` 判 `fail`。这条用例存在的意义是防止本次修复把检查的牙齿一起拔掉——只区分"还没有摘要"和"摘要对不上"，不放过真正的篡改。

**边界**：修复只改分类，不改任何写入语义、不改 ADR-0010 冻结的内容，因此不需要业主对备份语义的额外授权。候选修法 D（恢复时回填）与 E（预留移到快照之后）均未采用；E 会丢失崩溃可见性，D 需要对已恢复内容做写入。

## BP-048（2026-09-16）

### 已发布的迁移文件是内容寻址的，因此连注释也冻结

### 事实

Phase 5 复审提出一条修正（M2）：`migrations/0011_legacy_import.sql` 中 `legacy_event_integrity` 触发器的注释声称它阻止调用方记录"缺少 provenance、**deterministic identity** 与 corpus fingerprint"的导入，但该触发器实际上**无法**校验身份确定性——`legacyEventId` 是对规范化 JSON 做 SHA-256，SQLite 在这个位置无法重算。注释是一句实现不了的话。

按常规做法我直接改了这段注释。随后核对时发现这不是一个可做的动作：

1. `MigrationRunner` 对每个迁移文件取 **原始 SQL 文本**的 SHA-256（仅做 CRLF→LF 规范化），写入 `schema_migrations.checksum`；注释**计入**摘要。
2. 打开数据库时会逐条比对：`row.checksum !== checksum(readMigrationSql(migration))` 即抛 `MIGRATION_ERROR: Applied migration 1 does not match the local migration set`（`packages/store/src/migrations.ts`）。
3. 因此，**一次纯注释修改会让所有已应用过该迁移的数据库无法打开**——包括业主本机已经导入过语料的数据库。

该修改已**回退**（`git checkout -- migrations/0011_legacy_import.sql`），未进入任何提交。

### 同一原因造成的既有陈旧表述

`0011` 文件内另有两处文字与当前实现不一致，且**同样无法在本文件内修正**：

1. 触发器注释声称校验 "deterministic identity"（本轮 M2 所指的问题）。
2. 文件头注释称"A re-import of the same corpus is recognised by `(source_fingerprint, plan_hash)`"。Phase 5 复审已把幂等键改为**仅按 `source_fingerprint`**，并在 plan 不同时返回 `planDiffersFromRecorded`。

### 解决方案

1. **回退文件改动**，把 M2 的纠正写进 `docs/ADR/ADR-0012-phase5-legacy-migration.md`，并在 `docs/PHASE-5-GATE.md` 中列为"冻结文件中的陈旧注释"这一条已知偏差，指明正确表述的所在。
2. 立下规则：**任何已提交的迁移文件都是内容寻址的，不得为修正文字、格式或注释而编辑。** 修正一律写在 ADR／Gate／字段图里并交叉引用。行为变更必须作为**新版本迁移**落地，而不是编辑旧文件。

### 边界与后果

1. 这是**流程性断点**，不是运行时缺陷：`pnpm verify` 在注释被改、数据库全部失效的状态下**仍然会通过**，因为测试使用临时目录、每次全新建库。这正是它与 BP-044（工具链注入控制字节）同族的理由：**只在真实既有数据上才显形的破坏，不会进入断言，也就不会被发现。**
2. 它也解释了为什么不能"顺手"修 BP-047：托管备份语义由 ADR-0010 冻结，而冻结面不止代码，还包括这类内容寻址的产物。
3. 本条的处置方式（回退 + 记录 + 改在 ADR）与项目既有原则一致：**发现的问题记录为问题，不静默修改**；不能改的地方要说清为什么不能改。

## BP-049（2026-09-16）

### 两个构建器写同一个 dist，测试与类型检查可能对着陈旧代码运行

### 事实

1. 工作区包只导出构建产物：`packages/store/package.json` 的 `exports` 指向 `./dist/index.js` 与 `./dist/index.d.ts`。`vitest.config.mjs` **只**把 `@praxis/contracts` 别名到 `src`，`@praxis/store`、`@praxis/runtime` 等一律解析到 `dist`。
2. 每个包有两个构建器写同一个 `dist/`：
   - `pnpm build` 用 **tsup** `--dts` 生成**打包合并**的 `dist/index.d.ts`（`StoreHealth` 等类型被内联展开）；
   - `pnpm typecheck` 用 `tsc --build` 生成**逐文件**的声明，`dist/index.d.ts` 是 `export { ... } from "./sqlite.js"` 形式。
3. 增量构建下，`tsc --build` 只重发它认为变化的文件。实测：只改 `packages/store/src/sqlite.ts` 后运行 `tsc --build`，`dist/sqlite.d.ts` 被更新，而 tsup 留下的**打包版** `dist/index.d.ts` 原样保留。
4. `pnpm verify` 的顺序是 `format:check → lint → workspace:deps → boundaries → typecheck → test → build`，即 **test 在 build 之前**。
5. 后果一（本次实际撞上）：改完 store 的类型后运行 `pnpm verify`，`typecheck` 阶段报 `TS2339: Property 'unfinalizedReservations' does not exist on type '{...}'`——**错误指向的是正确代码**。用 `tsc --build --force` 强制重发后立即通过。
6. 后果二（本次也实际撞上）：改完包源码后直接 `npx vitest run`，测试跑的是**上一次构建的代码**。本次有三个用例因此报出假失败（"恢复失败"），而修复其实已经生效——同一机制的镜像面是**假通过**：源码改坏了、测试仍然全绿。

### 影响范围

CI 不受影响：干净的检出没有 `.tsbuildinfo`，`tsc` 全量发件，`dist` 与源码一致。这条断点只影响**本地增量迭代**（人或其他 agent）。因此它不会让错误的产物进入提交，但会让人对自己的改动**做出错误判断**——这正是它与 BP-044、BP-048 同族的理由：**只在特定状态下才显形的错配，不会进入断言。**

### 候选修法（待决策）

| 方案          | 做法                                                                 | 代价                                                                                                |
| :------------ | :------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| **A（推荐）** | 把 `pnpm build` 移到 `pnpm verify` 的 `test` 之前                    | 一行改动；让测试对着本次构建的产物运行。仍然保留"测试的是构建产物"这一语义                          |
| **B**         | 在 `vitest.config.mjs` 里像 contracts 一样把所有工作区包别名到 `src` | 彻底消除双写错配；但测试对象从"构建产物"变成"源码"，构建可运行性由 `verify` 末尾的 `build` 单独保证 |
| **C**         | 记录并维持现状，靠"改包源码后先 `pnpm build`"的人工纪律              | 零改动；但纪律不会传给下一个 agent，假通过/假失败会重演                                             |

推荐 A：改动最小，且不改变"验证构建产物"这一意图。B 更彻底但改变了验证对象。

### 边界

1. 这不是本次改动引入的问题，而是 `tsup --dts` 与 `tsc --build` 共存于一个 `dist` 的既有结构后果。
2. 本断点**不修改 `package.json` 或 vitest 配置**：`verify` 的定义就是本项目的验证门禁，改它属于扩大 Phase 5 范围，须由业主决定。
3. 本次的临时处置：`npx tsc --build tsconfig.build.json --force` 后再运行测试；此后所有结论均基于强制重发后的 `dist`。

## BP-055（2026-09-16，P5-OPEN）

**方法失败两例，均在本轮内被发现并纠正，未进入任何持久结论。**

### 一、扫描模式写错，于是"扫过了，干净"

P6-R0 §C 报告「worktree 内无本地绝对路径」。实际 `docs/SOURCE-MANIFEST.md` 有**四处** `C:\Users\35636\…`，含作者 Windows 用户名、真实姓名目录（`赖培胜选集`）与本地目录结构。

原因：双引号 shell 字符串里的 `"C:\\\\Users\\\\35636"` 被 shell 折叠成 `C:\\Users\\35636`，正则里的 `\3` 被当作**反向引用**；Git Bash 的 grep 对该模式既不报错也不匹配，直接返回空。是 P5-OPEN 用 `grep -F`（固定串）重扫时发现的。

**这条比它漏掉的东西更重要**：一个因为模式写错而返回"干净"的扫描，比不扫描更危险——它产出了一份带签名的结论。BP-050 的根因是"审查简报来自未读原文的理解"；这一条是它的孪生形态：**审查工具本身没有被验证**。此后所有安全扫描以此为准：先证明模式能命中已知样本，再相信它的空结果。

### 二、未经运行就宣布了一个"被静默忽略"的 flag

接线 ISSUE-085 时，我 grep 了 `commandLegacy` 处理器，发现 `--archive` 已列在 `flagsByCommand` 里却在该函数体内没有被读取，于是写下「a flag that is accepted and ignored」并准备登记为缺陷。

实际 `resolveEnvironment`（`apps/cli/src/index.ts` 第 97 行）早已读取它：`optionalFlag(parsed, "archive") ?? config.legacyArchiveRoot ?? …`。flag 一直是生效的，只是生效点在**解析环境**而非**使用环境**。

在写入记录前核对 `git show HEAD:apps/cli/src/index.ts` 时发现，改动已回退并改为一行注释说明该处是唯一读取点。

**教训**：`grep` 一个函数体只能证明**该函数体**没读它。一个 flag 是否被忽略，要用**运行**来证明（`--archive X` 后 archive 是否真的落在 X），不能用搜索来证明。
