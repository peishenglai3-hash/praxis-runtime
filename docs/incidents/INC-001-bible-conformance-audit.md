**Method:** Bible → Requirements → Repository Evidence → Test Evidence → Gate Decision

## 0. A numbering conflict that must be settled before reading this audit

The INC-001 recovery prompt's section 5.1 lists audit coverage under phase
headings that follow the **Correction Pack's** numbering, not the Bible's:

| INC-001 §5.1 heading | Topics listed there                                             | Bible phase that actually owns them |
| -------------------- | --------------------------------------------------------------- | ----------------------------------- |
| "Phase 2"            | Projection, snapshot, rebuild, agent cursor, replay determinism | Phase 2 (EPIC-003/004) — agrees     |
| "Phase 3"            | ContextPlan, reuse/reindex/refresh, ranking reasons, exposure   | **Phase 2** (EPIC-004)              |
| "Phase 4"            | OutcomeResidual, TimingResidual, RuleResidual, FieldContext     | **Phase 3** (EPIC-005)              |
| "Phase 5"            | ReflectionResult, STOP/CONTINUE/ESCALATE, budgets, runaway      | **Phase 3** (EPIC-006)              |
| "Phase 3.5"          | Actor≠Writer, ACL, Expectation, backup, purge, Node pin         | Phase 3.5 — agrees                  |

This is not a new error: `docs/PHASE-3.5-GATE.md:27-30` already records
`RFC MISMATCH: PHASE4_LABEL_DRIFT` for the same root cause — the Correction Pack
calls the residual phase "Phase 4" in its section 9. The recovery prompt
inherited that label.

**Resolution taken:** every topic the prompt lists is audited below, keyed to the
**Bible's** phase numbering, because the Bible is the controlling plan. Auditing
under the prompt's labels would have produced a matrix that mislabels Bible
requirements, which is the failure mode INC-001 exists to correct. Recorded as
`RFC MISMATCH: PHASE_LABEL_DRIFT_IN_RECOVERY_PROMPT`.

lag and asset provenance/drift, and **not** met for cursor corruption or schema
drift in the §13.1 sense.

### 9.2 The `config` check cannot fail (MEDIUM)

`apps/cli/src/index.ts:346-353` emits `status: "pass"` unconditionally, because
`loadConfig` throws before the check can observe anything. The _behaviour_ is
right — an unknown field does exit 3 — but the check is not evidence, and it
appears in every doctor report as a passed check. This is the same class as the
`expect(true).toBe(true)` smoke test fixed at `ded9ec6`: a check that cannot
fail.

### 9.3 Command paths with no executable coverage (HIGH)

Counted against `args.ts`, these have no test or script that invokes them:

asset list          asset contest          asset disable

`export` left this list at `ded9ec6`. Issues 082–086 are nonetheless marked

### 9.4 `legacy.pattern.imported` is an invented event type (MEDIUM)

Bible §5.4's taxonomy and §12 name `legacy.signal.imported` and
`legacy.graph-edge.imported`. `legacy.pattern.imported` and
`legacy.import.completed` are additions. They are defensible — a pattern must
land somewhere — but they are not registered as departures anywhere.

### 9.5 Bible §5.4's required event types, counted (MEDIUM)

A mechanical count of every occurrence of the 18 type strings Bible §5.4 lists
under 「MVP 必须包含的关键事件」, across `.ts`/`.sql`/`.json`/`.mjs`/`.md`

| `expectation.registered` | 35          | implemented                                                                                           |

| `context.plan.created`   | 21          | implemented                                                                                           |

| `reflection.rejected`    | **0**       | not implemented                                                                                       |

Two distinct problems are hiding in one table, and they are not equally serious:

1. **Naming.** Ten of the eighteen are implemented under a different verb — the
   Bible's past-participle state names (`asset.activated`) versus the
   implementation's imperative command names (`asset.activate`). The lifecycle
   semantics are present and tested; only the literal strings differ. This is a
   real deviation from a frozen taxonomy, and it is cheap to register.
2. **Absence.** Five types are genuinely absent: `reflection.accepted`,
   `reflection.rejected`, `privacy.tombstoned`, `privacy.purged`, and
   `expectation.resolved`.

The `privacy.*` pair deserves separate note. Bible §5.4 says they exist to make
deletion an explicit exception inside an append-first ledger. The implementation
records deletion in a **receipt table** instead. Both the Correction Pack §4.5(7)
and ADR-0010 specify exactly that receipt, so the _later author decision_
supersedes the Bible's event name — but the supersession was never registered,
and a table row does not participate in replay the way a ledger event does.
`reflection.accepted` / `reflection.rejected` have no such justification: Bible
§9 describes the runtime deciding whether to execute or escalate a proposal, and
that decision currently leaves no event.

**Required action:** for each of the fourteen non-identical strings, either
rename to the Bible's literal, add the missing event, or register a
`RFC MISMATCH` naming which document supersedes the Bible's name. Silence is
not an option under INV-10.
