# RFC 0001 Praxis Runtime Engineering Baseline

Status: Frozen for Alpha implementation

This RFC is the repository-facing engineering index for `Codex Implementation Bible v1.0`. The Bible remains the controlling plan. The supplied The Final documents are design provenance and review material, not executable instructions.

## Mission

Preserve local interaction history, reconstruct derived state deterministically, select context with explainable reasons, detect bounded and verifiable residuals, and promote validated reusable assets without removing human inspection or correction.

## Invariants

1. Raw history is append-first. Corrections are new events; privacy purge is an explicit exception.
2. Derived data is never presented as observed fact and keeps provenance.
3. Current state, snapshots, and context caches are rebuildable projections.
4. Actors may occupy different event cursors.
5. Residual magnitude and effect are independent; automatic effect defaults to `unknown`.
6. Rules, skills, workflows, and policies are challengeable, disableable, restorable, and forkable.
7. The user can inspect, contest, disable, restore, fork, export, and purge.
8. Core storage and contracts use engineering semantics, not theoretical terms.
9. Strong external verification can reject internal consensus.
10. Structural mismatches are reported as `RFC MISMATCH`; they are never silently compensated.

## Dependency direction

`contracts` is the lowest layer. Domain packages depend on contracts or explicitly allowed lower-level APIs. `runtime` is the only composition root for multiple domain packages. `apps/cli` and `apps/daemon` call runtime use cases and do not orchestrate domain packages directly. Provider SDK types remain inside adapters.

## Phase 1 boundaries and deferred gates

EPIC-002 is an event-material ledger, not an interpretation registry. Its `payload` is opaque JSON. `source` uses `SourceRef`, `evidence` uses `EvidenceRef[]`, `links` uses `EventLinks`, and `provenance` is required; these fields preserve source boundaries without classifying records as derived, candidate, or confirmed. That classification and the source-chain rules for projections belong to EPIC-003/004 and must be added before any derived state is treated as an observed fact.

An external `operationId` is an idempotency grouping key, not a row identity. One operation may contain one event for each lifecycle type, including `tool.requested`, `tool.succeeded`, and `tool.failed`; a retry of the same operation-and-type must be content-identical or fail explicitly. `lookupOperationState` reports the latest known tool lifecycle state without inferring success from the absence of failure.

Phase 2 keeps projection and context responsibilities separate. `ProjectionEngine` consumes the `EventReader` and `ProjectionPersistence` ports; it does not permit a reducer to call the clock, network, LLM, or random source. Projection persistence must reject stale or future cursors and use compare-and-swap semantics where a cursor can be advanced concurrently. `ContextPlanner` consumes candidate material and versioned ranking configuration, returns a complete plan snapshot with reasons and exposure proposals, and does not append events. Only the runtime composition root records `context.plan.created` and `context.item.exposed`; it verifies that referenced source events exist and that exposure provenance remains inferred/derived. Plan and exposure identities are deterministic for safe retries.

The `actor` in the Phase 1 envelope is a declared actor supplied by the caller. It is not an authenticated writer identity and does not constitute a permission decision. A trusted caller context and the distinction between declared actor and actual writer are deferred to the runtime/adapter boundary. In Phase 2, `packages/runtime` is the injectable domain use-case/composition boundary; production SQLite/config/clock/id/actor assembly and user-facing CLI/daemon workflows remain deferred rather than being implied by the façade.

The Zod contract is the executable validation gate used by the runtime and store. `schemas/event-envelope.v1.schema.json` is the structural interchange schema; it carries the same canonical timestamp lexical constraint and a `date-time` format annotation, but consumers must enable format assertion or use the runtime validator when calendar-valid timestamps are required. A schema-parity gate is required before external producers are admitted.

## Phase 3 contracts and runtime bridge

`packages/residual` implements only three automatic residual families from the Bible:

- `outcome` compares an observed value with a caller-declared expectation. Exact comparison is deterministic; predicate and external expectations require an explicit verification result.
- `timing` requires a relevant subscription and both a sequence lag and wall-clock staleness beyond declared thresholds.
- `rule` checks only declared event types and checkpoints within the requested trace. An empty or otherwise unverifiable rule produces no residual.

The detector keeps `magnitude`, `confidence`, `persistence`, `effect`, evidence, and field context separate. Automatic effect is always `unknown`; no detector result claims that a mismatch is harmful, productive, or neutral. `representation`, `relation`, and `retrospective` remain typed review categories and are not auto-adjudicated.

`packages/reflection` returns a `ReflectionResult` with `STOP`, `CONTINUE`, or `ESCALATE`, bounded hypotheses, support/counterevidence, testability, estimated cost, and permission labels on proposed actions. It enforces depth, hypothesis, tool-call, and elapsed-time budgets and stops when the same residual has no new event/evidence. It has no store, Agent, adapter, network, or tool execution dependency. `requiredPermission` is descriptive until a future authenticated control plane evaluates it.

`Phase3Runtime` is the only Phase 3 bridge that records derived events. `residual.detected` and `reflection.proposed` are append-first, provenance-inferred, evidence-linked, and idempotent. A reflection proposal must match a recorded residual event. The runtime never executes the recommended action or promotes an asset. JSON interchange shapes are fixed in `schemas/residual.v1.schema.json` and `schemas/reflection-proposal.v1.schema.json`; runtime/schema parity remains a gate before admitting external producers.

The Phase 2 context write boundary has a second, lower-level guard in migration `0005_context_event_integrity.sql`. Runtime semantic checks remain the primary gate; SQLite triggers prevent a direct EventWriter from inserting a context plan or exposure that lacks the candidate/source/provenance/plan-membership chain. This is an integrity guard, not authentication or ACL.

## Phase 4 implementation status

The Phase 3.5 Correction Pack froze the local capability semantics, structured
expectation/verification semantics, local CLI/daemon assembly, backup/privacy
boundary, and exact Node/CI target. The old precondition register in
`docs/PHASE-3-INPUTS.md` is retained as history and reconciled as closed for
local implementation; it is no longer a generic request for the owner to

Phase 4 is the Bible's EPIC-007 Reusable Assets scope. The implementation may
proceed locally under explicit owner instruction, with synthetic fixtures
clearly labelled as implementation evidence. Asset promotion still requires
the frozen runtime policy, provenance, validation, and human confirmation; no
synthetic fixture silently becomes authorial production evidence.

The formal Alpha/merge gate is `GO`: GitHub Actions run `34978723319` passed
the same `pnpm verify` on both the Ubuntu and Windows runners with exact Node
`22.13.0`. The owner has authorized synchronization of the source to the
private remote for controlled external-model handoff; that synchronization
does not imply public release.

## Phase 5 implementation status

Phase 5 is the Bible's EPIC-008 (audited Legacy migration) and EPIC-009
(command line, diagnostics and operational evidence). Both were implemented
under explicit owner instruction, with the first-generation source read
read-only and no first-generation record value entering the repository.

EPIC-008 was implemented against a field map derived from the public
first-generation source rather than from an assumption about its format; that
map is `docs/migration/LEGACY-FIELD-MAP.md`. The Bible's section 12 table names
four anomaly classes explicitly and describes a fifth condition without naming
it; four further classes were established from the corpus and are recorded in
`docs/ADR/ADR-0012-phase5-legacy-migration.md`: a byte-order mark, a CRLF
frontmatter anchor that the first generation's own readers cannot match, an
explicitly unmapped path, and material matched by a privacy rule. Folding any
of them into an existing class would have reported a parse failure as
"possibly overwritten" — a claim about history the evidence does not support.

The repository fixture is synthetic and byte-exact; `.gitattributes` marks it
`-text` so Git cannot normalise the encoding facts the importer must detect.
The owner's real corpus is never copied into the repository.

After implementation, the phase's results were reviewed by two independent
reviewers, one for engineering adaptability and one for intellectual
compliance. Both found real defects; the High findings were fixed with
regression tests (`tests/integration/phase5-review-fixes.test.ts`). Three
findings were escalated to the owner rather than fixed unilaterally, and are
set out in `docs/PHASE-5-GATE.md`:

- `BP-047` — a managed backup's snapshot carries its own unfinalized
  reservation, so it failed its own doctor gate. Pre-existing, ADR-0010.
  Owner decision: reclassify, so an absent digest is no longer read as a
  changed digest. Fixed, with a regression test that proves the check still
  catches real tampering.
- `BP-048` — a committed migration is content-addressed, so its comments are
  frozen and cannot be corrected in place. Avoided; the corrections live in
  ADR-0012 §5.1.
- `BP-049` — two build steps write one `dist/`, so local iteration can
  typecheck or test against stale code. Open: changing it changes what
  `pnpm verify` is.

EPIC-009 gives the command line a caller-visible contract: the Bible's exit-code
taxonomy, a stable error document, and a `--json` mode in which stdout carries
exactly one versioned machine document while every diagnostic goes to stderr.
`docs/ADR/ADR-0013-phase5-cli-diagnostics.md` records the decisions, including
one deliberate gap: Bible section 13.2's context-ranking weights, reflection
budgets and timing-residual thresholds remain package defaults because
threading them would change the verified Phase 3 and Phase 4 constructor
boundaries. That gap is named in the Phase 5 gate with its decision owner
rather than claimed as delivered.

## Known mismatches and resolutions

- `RFC MISMATCH: ADR_NUMBER_COLLISION`: existing ADR history was preserved;
  Phase 3.5 uses `ADR-0008` through `ADR-0010`.
- `RFC MISMATCH: SQLITE_BACKUP_API_VERSION`: the pinned Node `22.13.0`
  baseline uses `VACUUM INTO`; the later `DatabaseSync.backup()` convenience
  API is not used to justify a runtime upgrade. `node:sqlite` remains
  experimental in the pinned release even though the flag is no longer
  required.
- `RFC MISMATCH: PHASE4_LABEL_DRIFT`: a Correction Pack label says “Residual
  Engine”, while the Bible and delivery table define Phase 4 as EPIC-007
  Reusable Assets. The Bible controls the implementation.
- `RFC MISMATCH: ASSET_RESTORE_PERMISSION_SCOPE` was resolved in Phase 4 by
  adding a dedicated `asset.restore` scope and regression coverage. Restore is
  no longer silently mapped to `asset.propose`.
- `RFC MISMATCH: LEGACY_INPUT_NOT_IN_REPOSITORY`: the Bible names
  `codex-habit main@c3be4af` as the Legacy migration input, but neither the
  source nor the data was present in this repository. The owner authorised a
  read-only public fetch of the source. The field map was derived from it and
  the repository fixture is synthetic; the owner's runtime data remains outside
  the repository. Decision owner: the repository owner.
- `RFC MISMATCH: LEGACY_ANOMALY_CLASSES_EXTENDED`: the Bible's section 12 table
  has five rows. Four name a class explicitly (`possible_overwrite`,
  `ambiguous_pattern`, `source_metadata_conflict`, `unrecoverable_field`); the
  fifth describes a category cartesian relation and its handling without naming
  a class, and this implementation names it `cartesian_relation`. The audited
  corpus exhibits four further conditions the table cannot express
  (`parse_error`, `encoding_marker`, `unmapped_path`, `privacy_sensitive`), and
  they are implemented as distinct classes rather than folded into an existing
  one. Decision owner: the repository owner.
- `OPEN GAP: CONFIGURATION_SURFACE`: Bible section 13.2 names four knobs as
  operator configuration. The promotion threshold is delivered —
  `praxis.config.json` carries `promotionPolicy.minimumEvidence` and
  `minimumIndependentEpisodes` and the runtime honours them. The other three,
  context-ranking weights, reflection budgets and timing-residual thresholds,
  remain package defaults. Named in `docs/PHASE-5-GATE.md` with its decision
  owner; not silently claimed as delivered.

### Phase 5 departures registered on 2026-09-16

These were found by re-reading the Bible text against the tree after Phase 5
had been declared a local `PASS`. The first is the one that matters: it is a
departure the phase had been carrying as prose rather than as a mismatch, which
is exactly what Bible INV-10 forbids.

- `RFC MISMATCH: LEGACY_PATTERN_TO_CANDIDATE_ASSET`: Bible section 12 states
  「旧 patterns → candidate asset，不自动 active」, and issue 073's acceptance
  condition is "candidate asset / legacy.graph-edge.imported; 低 provenance".
  The implementation emits `legacy.pattern.imported` instead and creates no
  candidate asset. This is structural rather than an omission: the importer's
  frozen writer is `IMPORTER`, whose scopes are `system.migrate` and
  `event.read`, so no `asset.*` verb is reachable from the import path at all.
  The phase's gate had argued this was the Bible requirement "delivered as the
  consequence of that boundary", which is a defensible reading of the _intent_
  and not of the _text_. Under INV-10 that belongs here with a decision owner
  rather than in prose. Options: (A) keep the confinement and register this
  mismatch — the candidate-asset step stays an explicit, human-confirmed Phase 4
  action outside the import path; (B) add an explicit post-import step that a
  human runs to propose a candidate asset from a named imported pattern.
  Decision owner: the repository owner.
- `RFC MISMATCH: GOLDEN_FIXTURE_01_ABSENT`: Bible section 14 specifies Golden
  Fixture 01 — a sanitised minimal event set for the 《红色源代码：洪湖篇》
  art Production Card collaboration chain, with at least one counterexample
  ("a real task where the user asks to skip the Production Card") to prevent
  rule over-fitting. No such fixture exists in the repository, and the Bible
  states the handling for this case directly: 「素材不足 → 请求补素材」. The
  fixture cannot be synthesised without inventing the author's history, so it is
  requested from the owner rather than fabricated. Blocks Alpha exit criterion
  11 ("Golden Fixture 01 + 至少一个真实项目连续使用 ≥ 2 周"). Decision owner:
  the repository owner.
- `RFC MISMATCH: DOCTOR_COVERAGE_VS_13_1`: Bible section 13.1 lists ten doctor
  responsibilities and issue 081 requires doctor to cover
  "DB/schema/projection/assets/cursors/context/legacy". Delivered: DB state,
  WAL/PRAGMA, projection version/cursor/lag, asset provenance, legacy import
  integrity, config. Not delivered: `PRAGMA integrity_check` (present only on
  the backup path), busy-timeout assertion (reported, not checked), migration
  version _compatibility_, event-schema/content_hash sampling, stale-snapshot
  and orphan-`projection_data` checks, agent-cursor checks, and
  context-exposure orphan checks. The gate's issue-081 row claimed `PASS` for a
  coverage its own text did not demonstrate, and cited a "doctor check list
  below" that the document does not contain. Both are corrected in
  `docs/PHASE-5-GATE.md`; the missing checks are registered here rather than
  claimed. Decision owner: the repository owner.
- `RFC MISMATCH: CLI_SURFACE_GAPS_VS_13`: Bible section 13 specifies
  `praxis rebuild [--projection <name>]`, `praxis privacy purge <scope>
--confirm` and, in issue 085, a legacy import `report path`. The
  implementation accepts no `--projection` on `rebuild` (there is no way to
  rebuild a single projection), takes `purge --session <id>` rather than a
  positional scope, and writes the migration report to stdout and the run
  tables rather than to a report path. Decision owner: the repository owner.
- `RFC MISMATCH: TEST_LAYER_STRUCTURE`: Bible sections 3 and 14 freeze four
  test layers — `unit/`, `integration/`, `replay/`, `regression/`. The
  repository has `unit/` and `integration/` only; `tests/replay/` and
  `tests/regression/` do not exist and never have. Phase 5's regression cases
  live in `tests/integration/phase5-review-fixes.test.ts`. Pre-existing rather
  than introduced by Phase 5. Decision owner: the repository owner.
